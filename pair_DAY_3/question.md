## Context

In `training/train.py` (lines 77–78), the SFT script defaults to `training_data/sft_train.jsonl` and `training_data/sft_eval.jsonl` — a split built by randomly shuffling individual examples. The actual data is `preferences_train.jsonl` (1,172 pairs) and `preferences_dev.jsonl` (268 pairs), generated by distributing the ten Magpie variants of each probe 80/20 across train and eval.

This means the eval set contains paraphrases of training examples. Every eval example shares the same underlying probe as some training example: same Crunchbase signals, same correct ICP segment, same required funding reference. Only the surface phrasing differs.

`model_card.md` reports a best eval loss of **0.0213** at checkpoint-441, which was selected via `load_best_model_at_end=True` and published to HuggingFace. The held-out score of 78.8% is structurally clean — but whether the published checkpoint is the best-generalizing checkpoint or merely the deepest memorizer is an open question, because the checkpoint selection metric is corrupted.

## Question

In supervised fine-tuning on an augmented dataset, when you split train and eval at the **variant level** rather than the **probe level**, how does this corrupt the eval loss signal used for checkpoint selection — and what should you use as the checkpoint selection metric instead when a true held-out set already exists?

Knowing this will let me:

1. Fix `training_data/generate_full_training_data.py` to run a probe-level split (all variants of one probe stay on one side)
2. Replace the eval loss checkpoint callback in `training/train.py:207` with a rubric score from `scoring_evaluator.py`
3. Add a note to `model_card.md` clarifying that the reported 0.0213 eval loss is variant-level and cannot be interpreted as the generalization loss
